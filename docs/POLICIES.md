# 工作策略（本项目长期遵守）

> 记录于 2026-10-19。新仓库（`my-dsh`）里同样生效。

## 1. 处理任务的顺序：工具 → 模型 → 用户

1. **先用脚本/工具/软件**：能写成可重复执行的命令/脚本的，就不要让模型"手搓"。理由：可验证、可复跑、可进 CI、失败可定位。
2. **其次模型直接操作**：一次性、探索性、需要判断的事（读代码、试命令、改文件），由模型直接做。
3. **重要决策问用户**：不可逆、涉及取舍/成本/隐私/范围的事，先问再动。判据：
   - 会改变仓库结构、对外接口、或删除能力；
   - 花钱、动凭据、动别人可见的东西；
   - 有多种合理方案且代价差异大。

**反例（要避免）**：把"该写脚本的事"让模型一次次手敲；把"该我拍板的事"（比如删某个能力）自己决定。

## 2. 命名规则：内容优先，跨迁移通用

- 文件名/目录名描述**它是什么**，不写品牌、不写阶段代号；
- 通用到"换仓库/换底座不用改名"：`cli.sh`、`doctor.sh`、`export-repo.sh`、`check-upstreams.mjs`；
- 已有历史名（如 `mypi.sh`、`MYPI_*` 环境变量）**保持兼容**：新增别名/双读，不搞一次性大改名；
- 文档名同样按内容：`MIGRATION-MANIFEST.md`、`CAPABILITY-LEDGER.md`、`POLICIES.md`，不叫 `PHASE2-NOTES.md`。

## 3. 迁移时的分类规则

| 类别 | 处理 | 例子 |
|---|---|---|
| **直接进仓库** | 代码、配置、测试、文档——小而稳定、无外部依赖 | `assistant/`、`docs/` |
| **做成索引** | 大块内容、按需取用、或体积/许可不适合入库 | `packs/`（12MB 技能包）、旧会话（2.8MB） |
| **只记来源** | 有明确上游、可随时重新获取 | DSH 运行时（`runtime/`）、依赖包、工具链 |

**有明确上游的怎么快速检查更新**：用 `assistant/scripts/check-upstreams.mjs`（读清单 → 查 npm/GitHub → 输出"当前 vs 最新"）。
清单在 `docs/UPSTREAMS.md`（人读）+ 脚本内置（机读）。

## 4. 删除纪律

- 删能力前：先在 `CAPABILITY-LEDGER.md` 里写 `drop` + **删除前断言**，再删；
- 每次删除单独提交，`verify` 必须绿；
- 有数据的能力，先处置数据（迁移/冻结/删除）再删代码。

## 5. 事实源

- 新仓库（`my-dsh`）是**唯一开发事实源**；
- 老仓库（`my-pi`）冻结为只读参照，不再双向同步。
