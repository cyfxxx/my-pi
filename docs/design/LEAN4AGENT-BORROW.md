## 一、它在解决什么，以及关键设计选择背后的理由

**问题**（§1）：LLM agent 已被部署到高风险场景，但**多数 agent 系统缺乏"形式化地规定、验证、调试工作流与执行轨迹"的方法**。
现有手段各自只覆盖一部分：LLM-as-judge 易受幻觉与过度自信影响（尤其长程）；Hoare 风格契约只验工具调用；SMT 只验动作级策略；时序逻辑**无法表达数据依赖性质**。
⇒ 他们要的是一套**统一的**形式化基础（论文自称首个用**依赖类型形式语言**统一建模/验证/精化 agent 系统的框架）。

**两个部件**（Figure 1）：

| 部件 | 作用 |
|---|---|
| **FormalAgentLib** | 三层 Lean4 库（结构 / 语义 / 轨迹） |
| **LeanEvolve** | 用验证结果**修订工作流**（§2.3） |

**FormalAgentLib 的三层，以及@每层"谁做什么、什么被验证"**：

1. **Layer 1 结构验证**（§2.2.1）。把工作流建成**异质图** `G=⟨V,E⟩`，节点 `v_i=⟨r_i,w_i,t_i,τ_i⟩`（读变量、写变量、NL 指令、执行类型）；工作流 `W=(V,E,v_entry,X,P)`。
   用 Lean 归纳类型定义 `BaseType`/`StepType`（`step` = 带会话历史的 LLM 查询；`task` = 不带）与 `WorkflowNode`/`WorkflowEdge`/`WorkflowGraph`。
   验证的是**结构良构性**：节点可达、边合法、**读写一致性**（例如某节点读了既非初始参数、也非任何可达前驱产出的变量）——作者把它类比为"编译器的基本检查"。
2. **Layer 2 静态语义验证**（§2.2.2）。核心是 **Hoare 风格的前置/后置条件**：把每个 LLM 步骤建成语义节点 `s_i=⟨ρ_pre, v_i, ρ_post⟩`，并组织成**语义工作流图** `S=⟨G, s_para, S, L, C⟩`（含循环 `L` 与条件 `C` 节点，遵循 `Pratt (1976)`）。
   - **谓词系统**：`PredicateType`（`P`）为归纳类型，每个基谓词有解释函数 `toProp` 映射成 Lean 命题；用 `ext`/`PredicateKey` 支持**用户自定义谓词**（不改核心定义）；定义不清的用 `custom` 谓词（只做变量名存在性检查 + NL 说明留给后续 LLM 判断）。
   - **隐式变量与图级谓词**：**信息流谓词**（每步消费/产出哪些信息）与**上下文管理谓词**（某步可以观察哪些先前上下文）。作者原话：这类图级约束能发现"**连人类也会漏掉**"的上下文管理不一致。
   - **谁来标注**：**由 LLM 从 NL 步骤说明注释出前置/后置条件**（§2.2.2 末）。
   - **验证程序**依赖一个**显式假设 `LLMExec`**：若某 LLM 步骤在其前置条件满足的谓词上下文中执行，则它能产出满足后置条件的上下文。在该假设下，用**类型匹配 + Hoare 推理 + 辅助定理**自动证明静态语义自洽。
   - **一句关键让步（作者自己写的）**：Layer-2 **失败不等于工作流永远做不对**，只说明"**规格不是自洽的**"⇒ 定位为"支持 correct-by-construction 设计"，而不是"判定工作流好坏"。
3. **Layer 3 执行轨迹验证**（§2.2.3）。目的：**检验 `LLMExec` 假设在具体轨迹上是否成立**。
   - 基谓词与其组合 → **直接在 Lean 里求值**；
   - 超出 Lean 可判定核心的谓词（如 URL 连通性检查）→ **外部 Python 校验器**；
   - 只有 NL 定义的变量 → **LLM-as-judge**（可吃环境反馈，如 SWE 测试报错）；
   - 产出：**定位导致失败的那一步**（step-level 后置条件被违反）。

**LeanEvolve**（§2.3）：**触发条件是"工作流通过了 Layer-2，但在具体执行上给出错误/不确定结果"**。两种模式：
**formal-guided evolve**（用 Layer-3 的定位 + 可选环境反馈，让 LLM 改对应部分）与 **pure-LLM evolve**（不做形式化引导，逐步重写，用于允许多次尝试的场景）；改完**在同一问题上重跑**看是否解决。

## 二、实验与结论强度

**数据集**（§3.1.1）：SWE-Bench-Verified **随机抽 50 题的困难子集**（作者称这些题人类工程师通常需 >1 小时）；ELAIP-Bench（403 道选择题）**随机抽 100 题**（AI 论文理解）。

**方法**（§3.1.2）：让 LLM 独立生成**多个候选工作流** → 用工作流语言的 linter 过滤 → **自动生成 Layer-2 规格并验证** → 从通过者中**随机选 3 个**、失败者中**随机选 3 个** → **比较两组的任务通过率**。
第二组实验：SWE 有环境反馈，启用 pure-LLM evolve 报告累计解决率；论文理解任务**无细粒度反馈**，在**初始失败的 20 题子集**上比较 formal-guided 与 pure-LLM。

**实现**（§3.2，开头）：**Lean v4.20.0**；用 **Claude-Opus-4.6 生成 40 个工作流及 Layer-2 验证**；在 5 个模型上跑（含 GPT-5.2，此处被截断）。

**主要数字（来自摘要与 §1，§3.3 表格未读到）**：通过验证的工作流比未通过的平均高 **11.94%**（§1 给了更细的口径：SWE **14.80%**、ELAIP **9.07%**）；LeanEvolve 在 SWE 再提 **7.47%**（平均）。

**结论强度——我的评估（这是本节最该看的）**：

- **样本极小**：核心对照是 **3 vs 3 个工作流**。摘要说"extensive experiments"、§1 说"statistically significant"，但 **§3.3 与附录 A.2（95% CI）我没读到**，**无法核实**这个显著性是怎么算出来的。
- **对照存在混淆**：两组工作流都由**同一个 LLM 生成**，差别只在"是否通过验证"。通过验证的工作流很可能**本来就写得更仔细** ⇒ 11.94% 无法区分"验证带来了收益"与"更好的工作流更容易通过验证"。
- **作者自己的让步削弱了因果解读**：Layer-2 失败只说明"规格不自洽"（§2.2.2），**不说明工作流做不对**。那么"未通过组表现更差"就不能直接当作"验证提升质量"的证据。
- **LeanEvolve 的第二组对照只有 20 题**（§3.1.2）。
- **成本**：附录 **F Experiment Costs** 存在但**未读到** ⇒ 我**不能**说他们的成本是多少，也**不能**说他们便宜或昂贵。
- **未读到** §3.4 消融、§3.5 案例、附录 E 局限 ⇒ **消融与局限都无法转述**。

**小结**：这是一篇**方向性**论文（提出统一形式化框架 + 首套三层库），**不是**一篇"已用受控实验证明形式化验证能提升 agent 表现"的论文。它的价值在**框架与分层**，数字**不宜当作决策依据**。

## 四、可借鉴的（按性价比排序）

**A. 给关键工作流写一份"前置/后置条件"清单，并挂到既有守门上（推荐，成本低，零运行时改动）**
- **落点**：新建 `docs/design/WORKFLOW-INVARIANTS.md`；检查项挂进**既有**守门（`check-conventions.sh` 的第 E 节范式，或既有 opt-in 探针）——**不新增 golden 步**（步数被第 D 节钉住，加步会连带改多处计数）。
- **对象（5 个）**：重启续接、模式切换、子代理池、压缩/擦除、`goal` 自动续跑。每个 2–4 条"前置 ⇒ 后置"，**每条都必须能被机制化检查**（允许"仅提醒"但不允许只有散文）。
- **怎么验证（可重跑判据）**：每条不变量都要配一个**能被违反的坏样本**并证明守门会红——照 `custom/features/subagent/__tests__/wiring-args.test.ts` 的自证做法（该守门已实测：拿掉 `allowExtensions` 即红、恢复即绿，且**同一坏状态下 `tsc` 不报错**）。
- **参照**：这就是他们 Layer-2 的"**前置/后置对**"，只是**不做形式化证明**，用断言 + 守门实现。
- **成本/风险**：低（文档 + 既有守门扩展）；风险是写成空话 ⇒ 用"必须有坏样本"这条硬约束防住。
- **是否改默认行为**：**不改**。

**B. 把"读写一致性"搬到我们的注册面上（成本中，需先定数据源）**
- **做法**：`check-dead-exports` 已经管"写了没接线"；可再加一条**消费侧**检查——**声明面上存在、但最近 N 天调用数为 0 的工具**（数据源已有：`portable/memory/stats/tool-count-localhost.json`，P4 审计用过：`enable_tool` 30 天 8 次、`tool_search` 0 次但当时刚启用）。
- **怎么验证**：合成 stats 夹具 + 断言"零消费的声明工具会被点名"；并**先跑一次真实数据**看会点名谁（预期会命中 `verify_*` 已删这类历史，以及新启用未满窗口的工具——**启用时间必须与统计窗口对齐**，否则会把新机制误判为死机制，这条在 P4 已写过）。
- **成本/风险**：中；风险是**误报**（沉默期/新启用）⇒ 只提醒不阻塞。
- **是否改默认行为**：不改（只加守门输出）。

**C. "通过验证但结果错"的显式入口（成本中，需先读论文 §3.5 与附录 C）**
- **做法**：在 `goal` 的 `blocked`/`advisory` 路径上，附上"**最近一次被破坏的不变量候选**"（依赖 A 已落地）——对应他们"Layer-3 定位失败步 → 交给 LLM 改"的链路。
- **为什么现在不做**：A 没做之前没有地基；且他们这条链路的形态（怎么把定位结果喂给 LLM）在 **§3.5 案例与附录 C** 里，**我未读到**。
- **是否改默认行为**：会改（`goal` 返回值多一段），故必须先出提案让你点头。

## 五、明确不该照搬的，以及决定可不可照搬的关键缺口

**不该照搬**：

1. **引入 Lean4 做形式化证明**。理由是**工程成本与收益不成比例**：需要 Lean v4.20.0 工具链、维护一套自研库（他们附录 B 有大量类型定义）、还要**先用 LLM 生成 40 个工作流**来 bootstrap（§3.2）。my-pi 是**个人助手**，我们真正的短板是"**不变量没被写清楚、没被机制化**"——A 条用断言 + 守门就能拿到大部分价值，**不需要证明**。
2. **把 Layer-2 验证当门禁（gate）**。论文自己说：**失败 ≠ 工作流做不对，只说明规格不自洽**（§2.2.2）。拿它当"通过/拒绝"的闸门会**误杀**；我们现有的判据（`goal` 三态 + 命令校验优先 + 独立评审第二来源 + fail-open）方向更稳。
3. **把 LLM-as-judge 当主要判据**。他们也是"基谓词 Lean 求值优先，NL 变量才用 judge"（§2.2.3）；我们同样把**确定性检查**放第一优先、评审放第二来源（`docs/design/SUBAGENT-VERIFIER-CONTRACT.md`）——**这一点我们比照他们更保守，别退回去**。
4. **benchmark 驱动的 workflow 演化**：我们没有 benchmark、没有"任务分数"（WikiSkill 那篇的分析里已论证过同一件事）。
5. **照抄他们的实验范式**：**3 vs 3 个候选工作流**的核心对照，在我们这里既无统计效力也不可复现为决策依据。

**决定可不可照搬的关键缺口（我没读到，且它们直接影响判断）**：

- **附录 F Experiment Costs**：形式化验证的工程成本到底多大？（**未读到**）
- **附录 E Limitations**：作者自己承认的限制是什么？（**未读到**）
- **§3.4 消融**：Layer-2 的图级谓词、pure-LLM evolve 各自的贡献？（**未读到**）
- **代码**：`BaseType`/`StepType` 的具体定义、`LLMExec` 公理的写法、YAML 工作流格式与我们的工具面能否对接？（**不可达**）
- **是否需要外部求解器/网络**：他们用到**外部 Python 校验器**（§2.2.3）与 **LLM-as-judge** ⇒ 若照搬，就引入**外部进程依赖**；这一点对我们尤其敏感（我们的纪律是"失败开放、默认关闭"，见 `run-check.ts` 的 fail-open 与 120s 上限）。
