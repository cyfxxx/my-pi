# 三个"未迁移子系统"的处置（用户批复第 3 项）

> 2026-10-08。用户批复："查看这三个子系统，**有用就迁移**，无用则记录理由并按白名单规则处理。"
>
> 结论先说：**三个都不迁移**，但**理由各不相同**，且都是**实测**得出的——其中第 3 个还推翻了我自己
> 最初的解释（下面单独记）。每个的理由已写进 `scripts/dead-exports-allowlist.txt` 的对应行（棘轮所在处）。

## 一、JSON 结构性压缩（`compactJson` / `jsonBytes` / `shrinkHalf`）

**现状**：**零生产调用点**。截断路径（`pruneToolOutput`）统一走 head+tail。曾留的接入前提是
"需先定**哪些**工具输出按 JSON 压缩"。

**实测（本次回答的正是这个前提）**：扫描归档目录里**已经被截断过**的输出（归档只在截断时发生，
所以这批就是该优化唯一能服务的总体）：

```
归档输出 563 个；≥2KB 的（即被截断过的大输出）99 个
其中**能解析为 JSON** 的：0 个（0.0%）
≥20KB 的 5 个，其中 JSON 0 个
```

⇒ **没有服务对象**：my-pi 的大输出是命令输出/代码/日志，不是 JSON。接了就是纯死代码。
**决定：不迁移。**

## 二、Best-of-N judge（`DEFAULT_JUDGE_PROMPT` / `parseJudgeScores` / `shouldVerify` / `ProgressTracker` / `recordVerification`）

**现状**：**一半是接了的**——`bestOfN`、`selectBest` 由 `verify-tools.ts:210` 调用；
但 **judge 是注入式参数**（`judge?: (prompt, candidates) => Promise<CandidateScore[]>`），
生产里**没有默认实现**。缺的正是这 5 个导出：默认提示词 + 输出解析 + 门控 + 进度 + 记录。

**实测**：

```
30 天工具调用：verify_test 1 / verify_config 1 / verify_report 1 ⇒ verify_* 合计 **3 次**
（验证器本身默认关闭，需 verify_config(enabled=true) 才启用）
```

⇒ 为一个 30 天被用 **3 次**、且默认关闭的能力补上服务端 judge，**需求侧不成立**。
**决定：不迁移**（保持"judge 可注入"的现状——它让 `verify_test` 能工作，只是没有内置 judge）。

**但这里有一个**更有价值的用法**（提案，未实施）**：这 5 个导出缺的那一半，正好也是
**P1（`goal complete` 的 `verified` 态）所缺的第二校验来源**——P1 当时明确把"把 `verify_*` 接成
第二来源"列为后续项。具体设想：
- `goal complete {verify: true}`（P1 已预留语义）→ 用 `DEFAULT_JUDGE_PROMPT` + `parseJudgeScores`
  组一个 LLM 评审，把结果作为 `verified` 的**第二来源**（确定性命令是第一来源，优先级更高）；
- `shouldVerify(failCount, config)` 正好可做门控（"失败 N 次后才值得花一次评审"）。
- **当前阻塞**：需要一条**从工具调用模型**的通道。my-pi 现有路径是**派子代理**（`subagent`，起一个
  子进程调模型）——可行但成本是一次子代理运行；直接 provider 调用在本仓库没有现成客户端。
  因此这是一份**需要产品决策 + 一条通道**的提案，不是随手能接的线。

⇒ 结论：**不迁移，但把"迁移它的正确落点"记录下来**（落点在 goal 的第二校验，而不是 `verify_test`）。

## 三、记忆合并（`resolveAndApply` / `mergeCandidates`）

**现状**：生产写路径只用 **确定性的 `jaccardSimilarity > 0.7`** 去重（`storage.ts:221`）；
`decideMerge`/`resolveAndApply`（含矛盾取代、标题匹配、mem0 风格动作）**未接线**。

**实测（104 条真实记忆）**：

```
jaccard > 0.7（现有网应拦住的近重复）: **0 对**
0.4–0.7（"相似度合并可能有用"的缺口）:  47 对
```

**我最初的解释是错的（值得记下来）**：我看到 47 对里不少条目共享同一来源（`[CISA官方群]`、
`[GitHub安全公告]`），就推断"相似度来自**来源样板**，去掉前缀就没了"。
**验证后否掉了**：把 `日期。来源：[X]` 前缀剥掉再算，47 → **46 对**，最高相似度仍 0.58–0.63。
**真实原因**（看最高相似的前 3 对即可确认）——**它们是不同的 CVE**：

| 相似度 | A | B |
|---|---|---|
| 0.583 | `CVE-2026-88772` Citrix NetScaler Improper Restriction… | `CVE-2026-88779` Citrix NetScaler Improper Restriction… |
| 0.571 | `CVE-2026-88771` Citrix NetScaler Improper Input Validation | `CVE-2026-88779` Citrix NetScaler Improper Restriction… |
| 0.558 | `CVE-2026-59347` VMware 栈溢出 | `CVE-2026-59346` VMware 整数溢出 |

同产品、同漏洞类别、同来源模板 ⇒ **词面相似度天然很高**，但**条目是彼此独立的**。

⇒ **决定：不迁移。** 理由不是"没人用"，而是**这个语料上"相似度"是危险信号**：
最高相似的条目都是**不同的技术公告**，任何基于相似度（无论 jaccard 还是 LLM judge）的合并
都有**合并掉不同 CVE** 的风险——那是**不可逆的信息损失**，比"留着两条"糟得多。
而"重复"这个问题目前**根本不存在**（jaccard>0.7 零触发）。

**如果将来记忆语料变成"人写的、会长篇重述同一件事"的形态**，这条结论需要重新评估——
届时该测的是"**同一件事被重述**的比例"，而不是"词面相似度"。

## 四、方法上的收获

这一项的价值有一半在**流程**：我先给第 3 个子系统编了一个听起来很合理的解释（共享来源样板），
**跑一次验证就被否掉了**，真实原因是"不同 CVE 共用公告措辞"。
如果我没验那一下，`DECISIONS` 里留下的会是一个**错的理由**——而理由错了，将来据此做的判断也会错。
**"看起来像"与"测出来是"是两件事。**
