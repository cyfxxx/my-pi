## 3. 证据三：`fail/run` 高比值的来源 = 累计计数 + 同一到期时刻被并发触发 ✗

`runCount`/`failCount` 是**累计值、从不重置** ✓（`tool-stats-daily`: `run=50 fail=28` ✓）⇒ 修复后**仍会显示高失败率** ✗（历史包袱 ✓）。

更关键的是**同一到期时刻被触发多次** ✗（`tasks.json` 的 `history` 原文 ✓）：

```
2026-10-11T01:07:44.449Z | result=failed | ms=1713
2026-10-11T01:07:44.477Z | result=failed | ms=553
2026-10-11T01:07:44.498Z | result=failed | ms=710
2026-10-11T01:07:44.525Z | result=failed | ms=872
```

⇒ 4 条**落在 76 ms 内**、而单条耗时 **553–1713 ms** ✓ ⇒ **时间上互相重叠** ✓ ⇒ **并发执行** ✓（不是顺序重试 ✓）。
日志簇的规模也一致 ✓：`golden-fast` 10-10T10:06Z **8 条** ✓、`daily-health` 10-10T10:21Z **8 条** ✓、
`tool-stats-daily` 10-11T01:07Z **8 条** ✓ ⇒ **一次到期被跑约 8 遍** ✗，每遍都各自 **+1 run、+1 fail** ✓
⇒ `fail/run` **≈ 必然偏高** ✓（例如 `golden-fast` 24/44 ✓）。
**成因（本会话已定位 ✓）**：锁的 **TOCTOU**（`existsSync→读→unlink` 不复核 ✗ ⇒ 两方都以为持锁 ⇒ 双跑 ✓）
＋ **多实例/多 worker 同刻启动** ✓；两者**已在今天修掉** ✓（`locks.ts` 的"比较后再删 + 建锁后回读校验" ✓、
"只信任正面白名单入口" ✓、`PI_LOCK_DISABLE_PROC` 可移植存活判定 ✓）。
