# ObservationPack 对照审计（P3）

> 2026-10-08。对照 NVIDIA SoL-Pi 的 ObservationPack 机制，审计 my-pi **已有**的工具输出归档。
> **本文只审计与提案，不改任何默认行为/阈值**（方案第 1 节的边界）。
>
> SoL-Pi 的做法（项目页）：大输出**本地归档**，上下文里留 **handle + 短摘录**，需要时**分页精确召回**；
> 实现规格 **315 行 / 2 个钩子 / fail-open 契约**，且经过 **8 配置权衡扫描**才定版。
> 它的核心论点是：大结果"在之后每个请求里重复出现，同时占用上下文与缓存"。

## 一、我们已有什么（实现事实，均注明落点）

| 能力 | 现状 | 落点 |
|---|---|---|
| 归档原文 | ✅ 写 `<hash>-<len>.txt`，两层子目录 | `budget/output-archive.ts:38` `archiveOutput` |

**比 SoL-Pi 多的两处**：写盘前脱敏、内容哈希去重。后者恰好回答了它的核心论点——**同一个大输出重复出现时，
归档侧只占一份**（`existsSync` 直接复用），重复的代价落在"上下文里的句柄"而不是"磁盘或原文"。

## 二、审计清单逐条结论（含证据）

### 1. 上下文里留的是句柄还是只有一句"已归档"？→ **是句柄，但缺摘录**

句柄 = **绝对路径 + 字符数**（`原文 12345 字符已存档: /root/my-pi/portable/memory/tool-outputs/ab/<hash>-12345.txt`），
模型据此**能**召回，也知道少了多少。

**缺的是 SoL-Pi 的 `short excerpt`**：模型必须先读回才知道内容是不是它要的——这是"保留访问"与
"免一次读回"的差别。

### 2. 召回是整篇还是分页？→ **实测：两种都没发生——召回本身极少**

从全部 4 个会话文件里扫"引用了 `tool-outputs/` 的工具调用"：

```
会话文件数: 4
引用 tool-outputs 的工具调用: 2 次（涉及 1 个会话）
其中带 offset/limit（分页读回）: 0 次
按工具: {'bash': 2}
```

两点结论：
- **召回极罕见**（4 个会话里 2 次）——**样本太小，不足以支撑任何阈值决策**，这是本项最该如实说的话；
- **0 次分页**，而且**两次都走 `bash`**（`cat`/`head` 之类）而不是 `read`。说明模型把归档当"一个文件"，
  **完全没有把它当"可按页读的来源"**。句柄里没有任何分页提示（`read` 的 offset/limit 也没被提到）。

### 3. fail-open 是否写死并有测试？→ **写死了，测试也有**

`archiveOutput` 的 `try/catch → return null`、`archivedStub` 在 `path === null` 时只返回 `base`；
`sweepArchive` 注释明确"任何单文件失败都忽略（fail-open），不影响会话启动"。
`output-archive` 相关用例在 `context/__tests__/` 下（归档路径注入用 `PI_OUTPUT_ARCHIVE_DIR`）。

### 4. 默认是否开启、阈值多少？→ **默认开启**，触发点是"单条输出预算耗尽"

不是独立的"归档阈值"，而是 `pruneToolOutput` 在**会话输出预算已满**或**单条超限**时，
先做头尾截断、再把**原文**归档、然后把句柄写回上下文（`budget.ts:300-310`）。
历史擦除另有 60K/30K 两个阈值（`prune.ts:21-22`），与归档是不同机制。

### 5. "同一大输出在后续请求里重复出现"有多少？→ **归档侧已去重；上下文侧的重复由截断/擦除负责**

直接测"归档目录"这一侧：**563 个文件 / 3.4MB**（`find` + `du`）——归档在真实使用中**是活跃的**。
由于文件名含内容哈希，**同一内容只会有一份**；因此"重复出现"的代价不在归档，而在
**句柄被每个后续请求重放**（几十~几百字节 × 后续请求数），这正是 SoL-Pi 想用"handle 取代 body"解决的问题——
而我们**已经在做**（把 body 换成 handle）。

## 三、决策提案（**均不改默认**，等用户点头）

| 编号 | 提案 | 依据 | 代价 / 风险 |
|---|---|---|---|
| **P3-A** | 句柄加**短摘录**（首 200–400 字符，换行折叠） | SoL-Pi 的 handle = path + short excerpt；我们只有 path | 每次截断多 ~200 字符进上下文（一次性、在尾部）；摘录可能含敏感内容→**必须走同一个 `scrubSecrets`** |
| **P3-B** | 句柄明示**可分页读**（提醒 `read` 支持 `offset`/`limit`） | 实测 **0 次分页**、两次都走 `bash` | 文案长度 + 依赖模型遵循提示；若模型仍走 bash，收益为 0 |
| **P3-C** | **不动** 阈值（30K/60K 与"预算耗尽"触发） | 召回样本只有 2 次 | 缺证据时改阈值属赌博；**本项明确建议不改** |
| **P3-D** | 加**召回计数**（记录谁读了归档、是否分页、读了多少字节） | 让 P3-A/B 的效果**可被持续观测**，而不是靠 2 次样本判定 | 属"新增测量"，**我可以自己实施**（不触碰默认行为） |

**建议顺序**：先 **P3-D**（拿到可观测数据）→ 再决定要不要 **P3-A/B**（它们都是"改句柄内容"，
属改默认行为的边缘：虽只加文字，但会改变提示词/上下文内容）。**P3-C 建议保持不动。**

## 四、本次审计的实测数字（能力地板之外的"效率指标"）

- 归档目录：**563 文件 / 3.4MB**（说明归档在真实使用中活跃，不是死代码）；
- 召回：**2 次 / 4 个会话文件，0 次分页，2 次走 bash**（说明"分页召回"这条**尚未被使用**）；
- 去重：靠文件名内容哈希 + `existsSync` ⇒ 同一内容**只占一份**（机制性事实，非统计）。

**能力地板**：`tsc` / `vitest` / `check-features`（文档链接）/ `check-conventions`（第 D 节计数）/ `golden`。
本项为**纯文档 + 审计**，无代码行为变更。
