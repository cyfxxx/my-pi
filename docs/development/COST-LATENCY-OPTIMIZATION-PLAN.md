# my-pi 成本与效率优化方案（2026-10-01）

> 依据：本轮四份证据——DSH 运行时审计（351 行，`file:line` + 真实会话日志）、pi/my-pi 运行时审计
> （789 行）、my-pi 运行数据统计（`.usage-diag.jsonl` / `prefix-fingerprints.jsonl` / 全部会话）、
> 上游体检（`check-upstream.sh`）。
> 目标不是"多写机制"，而是把**已知的浪费**逐条消掉，并用可复现的数字证明。
> 纪律：不牺牲防退化（每项都带守门）、不动 `vendor/`（必须改就走补丁）、运行时状态不入库、
> 不引入需要在会话中途改写已发送历史的动作。

## 一、当前基线（同一模型 `deepseek-flash`，实测）

| 指标 | DSH（主会话） | my-pi | 差距 |
|---|---|---|---|
| 逐请求命中率 p50 / p05 | 0.999 / **0.978** | 0.9968 / **0.148** | 尾部差 6.6× |
| 未命中 p50 / p90 / p99 / max | 258 / 1,323 / 5,516 / **34,083** | 374 / 2,770 / **203,636** / **316,053** | 尾部差 9–10× |
| 静态前缀（system+工具）冷启动 | **134**（跨会话已缓存） | **8,865–23,093**（每次会话都不同） | 65–170× |
| 全价 token 占比 | 0.22–0.55% | **4.98%** | 9–22× |
| 上下文/请求 p50 | 264K | 132K | 我们家窗口用得浅 |
| 每轮步数 / 零工具调用步 | 51.6 / 2% | 14.8 / **9%** | 自主度 |
| 自动继续步延迟 p50 / p90 | 4.9s / 24s | 5.9s / **37s** | 延迟 |
| 工具声明 | 27 个 / 6.8K token | **63 个 / 6–19K token** | 前缀最大构件 |

> **2026-10-01 口径修正（Phase 0 完成后）**：`head` 分不清「改写」与「头窗内追加」，旧口径把 19 次追加误报成断裂；
> 按新口径（`segments` 分叉定位 + 剔除 head）重算 763 条记录，**真实前端断裂 14 次 = `system` 9 + `tools` 5**，
> **冷启动 20 次**（进程首请求，每次都重发整个静态前缀）。后续优化以此为基线。

**一句话**：稳态已经同级，问题全部集中在**尾部**——`input>10K` 的 60 条请求（6.5%）吃掉 **90.3%** 的未命中，
`>100K` 的 24 条（2.6%）吃掉 **73.6%**。所以优化的唯一正确姿势是：**先把尾巴看得见，再逐条掐掉**。

## 四、验证方法论（避免自欺）

1. **口径固定**：所有对比都用 `deepseek-flash` 单模型子集 + 同一统计脚本（`/tmp/dsh-stats.py`、`/tmp/pi-stats.py` 的思路固化进 `scripts/`）。
2. **A/B**：改前改后各至少 3 个会话/200 请求；对比 `input` 的 p50/p90/p99/max 与 p05 命中率，而不是只看均值。
3. **反例检查**：任何"命中率提升"都要排除"上下文变小了"（同时看 `contextTokens` 与 output）。
4. **日志坑**：DSH 侧剪枝会以新时间戳重发同 `callId` 的 `tool/result`，配对必须取**首个**；我们自己的指纹日志同样要防"重发导致误归因"。

2. **P3-1（自主度）**：如果确认是"早汇报"习惯拖累了每轮步数，改动会涉及 `AGENTS.md` 的对话纪律（你的偏好）。→ 需你确认边界。
