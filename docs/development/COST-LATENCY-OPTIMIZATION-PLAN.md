# my-pi 成本与效率优化方案（2026-10-01）

> 依据：本轮四份证据——DSH 运行时审计（351 行，`file:line` + 真实会话日志）、pi/my-pi 运行时审计
> （789 行）、my-pi 运行数据统计（`.usage-diag.jsonl` / `prefix-fingerprints.jsonl` / 全部会话）、
> 上游体检（`check-upstream.sh`）。
> 目标不是"多写机制"，而是把**已知的浪费**逐条消掉，并用可复现的数字证明。
> 纪律：不牺牲防退化（每项都带守门）、不动 `vendor/`（必须改就走补丁）、运行时状态不入库、
> 不引入需要在会话中途改写已发送历史的动作。

## 一、当前基线（同一模型 `deepseek-flash`，实测）

| 指标 | DSH（主会话） | my-pi | 差距 |
|---|---|---|---|
| 逐请求命中率 p50 / p05 | 0.999 / **0.978** | 0.9968 / **0.148** | 尾部差 6.6× |
| 未命中 p50 / p90 / p99 / max | 258 / 1,323 / 5,516 / **34,083** | 374 / 2,770 / **203,636** / **316,053** | 尾部差 9–10× |
| 静态前缀（system+工具）冷启动 | **134**（跨会话已缓存） | **8,865–23,093**（每次会话都不同） | 65–170× |
| 全价 token 占比 | 0.22–0.55% | **4.98%** | 9–22× |
| 上下文/请求 p50 | 264K | 132K | 我们家窗口用得浅 |
| 每轮步数 / 零工具调用步 | 51.6 / 2% | 14.8 / **9%** | 自主度 |
| 自动继续步延迟 p50 / p90 | 4.9s / 24s | 5.9s / **37s** | 延迟 |
| 工具声明 | 27 个 / 6.8K token | **63 个 / 6–19K token** | 前缀最大构件 |

> **2026-10-01 口径修正（Phase 0 完成后）**：`head` 分不清「改写」与「头窗内追加」，旧口径把 19 次追加误报成断裂；
> 按新口径（`segments` 分叉定位 + 剔除 head）重算 763 条记录，**真实前端断裂 14 次 = `system` 9 + `tools` 5**，
> **冷启动 20 次**（进程首请求，每次都重发整个静态前缀）。后续优化以此为基线。

**一句话**：稳态已经同级，问题全部集中在**尾部**——`input>10K` 的 60 条请求（6.5%）吃掉 **90.3%** 的未命中，
`>100K` 的 24 条（2.6%）吃掉 **73.6%**。所以优化的唯一正确姿势是：**先把尾巴看得见，再逐条掐掉**。

## 三、分阶段执行

### Phase 0 — 度量闭合（先让尾巴可见；零行为风险）

| 项 | 改法 | 判据 |
|---|---|---|
| P0-1a | `prefix-fingerprint.ts` 增加**全消息序列分段指纹**（按 N 条一段的滚动摘要 + 段级变更定位），`total` 兜底改为独立判据（不再依赖 `changed` 为空） | 大未命中（`input>10K`）的**归因覆盖率从 <50% 升到 ≥95%**（用现有 763 条历史回放验证） |
| P0-1b | 把"归因结论"写进 `daily-health` 输出（本次新增的变更点类型 + 次数） | 输出里能看到"哪类前端变更导致了多少未命中" |
| P0-2 | `daily-health.mjs` 增加**冷启动未命中**与**每会话断裂次数**两项（数据源：会话首请求 + 指纹日志） | 输出含 `冷启动=…次/…token`、`断裂=…次` |
| P0-3 | 更正 `CONTEXT-MANAGEMENT-COMPARISON.md` 三处结论；把两份审计落到 `docs/development/` | 文档链接门通过；三处结论与代码一致 |

| ~~P1-2~~ ✅ | （已完成）去重改为默认关闭，仅 `PI_CONTEXT_DEDUP_SUMMARIES=on` 启用 | 门控 3 例测试通过；该路径默认不再产生断裂 |

### Phase 2 — 静态前缀体积与变更频率

| 项 | 改法 | 判据 |
|---|---|---|
| P2-1 | 工具描述压缩专项：定 spec（描述 ≤N 字符、去掉重复模板话术、参数 description 精简），逐个工具过一遍；**不做分层**（分层会主动制造工具数组变化） | 工具声明总量从 6–19K token 降到 **≤6K**；工具选择质量不退化（抽查任务成功率） |
| P2-2 | 给 `AGENTS.md` 段与 `skills` 段加体积预算（超限时截断并显式提示，DSH 式），并在 `check-features`/golden 里立阈值 | AGENTS.md 超过预算会被守门拦下 |
| P2-3 | 重试策略复核：评估"重试前删投影"是否值得改成"保留投影 + 标记重试"（缓存优先） | 记录结论到 DECISIONS |

### Phase 3 — 执行效率与体验

| 项 | 改法 | 判据 |
|---|---|---|
| P3-1 | 自主度专项：先做**归因**（统计每个用户轮在什么条件下停下：是否 plan/todo 未完成就交回、是否被"简短回答"规则诱导），再决定是否加"未完成不收尾"的硬门 | 每轮步数中位数提升；干预率不升 |
| P3-2 | 步延迟拆解：把 37s p90 拆成"前缀重放 prefill" vs "工具耗时" vs "生成"，再决定是否给 `bash` 加默认超时或提示 | 拆解报告 + 优化后 p90 下降 |
| P3-3 | 子代理 fork 模式（继承历史、复用前缀）——上游已有 `fork` 能力则接线 | 子代理首请求未命中显著下降 |

### Phase 4 — 防退化收尾

- 每条修复补 vitest/golden 守门；`DECISIONS.md` 留记录；`PROGRESS.md` 分批；`VISION.md` §4 指标随动。
- 完成后跑一轮"全量验证 + A/B 复盘"，把收益写回本文件顶部基线表。

## 四、验证方法论（避免自欺）

1. **口径固定**：所有对比都用 `deepseek-flash` 单模型子集 + 同一统计脚本（`/tmp/dsh-stats.py`、`/tmp/pi-stats.py` 的思路固化进 `scripts/`）。
2. **A/B**：改前改后各至少 3 个会话/200 请求；对比 `input` 的 p50/p90/p99/max 与 p05 命中率，而不是只看均值。
3. **反例检查**：任何"命中率提升"都要排除"上下文变小了"（同时看 `contextTokens` 与 output）。
4. **日志坑**：DSH 侧剪枝会以新时间戳重发同 `callId` 的 `tool/result`，配对必须取**首个**；我们自己的指纹日志同样要防"重发导致误归因"。

## 五、需要用户决策的两处

1. **P1-1（AGENTS.md 迁出 system）**：这是收益最大的一条，但改变了提示注入的位置与形式，可能影响 agent 行为。建议做，但要 A/B + 人工抽查。→ 需你点头。
2. **P3-1（自主度）**：如果确认是"早汇报"习惯拖累了每轮步数，改动会涉及 `AGENTS.md` 的对话纪律（你的偏好）。→ 需你确认边界。
