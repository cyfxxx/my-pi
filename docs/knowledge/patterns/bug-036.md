# 失败模式：**迁移验证的三个陷阱

**来源**：`docs/BUG-REPLAYS.md` 第 36 条（使用层面故障台账，代码检查全绿但用起来才炸）。

**是什么**
**迁移验证的三个陷阱

**根因（WHY）**
会得出"数据丢了"的错误结论（其中两个是静默的）**：从一块损坏的 exFAT 盘做救援备份后对账，同一个事实被误判了三次。① **单位口径**：robocopy 的 `g` 是 **GiB** 不是 GB（`516.014 g` = 554.07 GB），用 `字节/1GB` 对账会看到"少 2.5 GB"的假差异；② **`EnumerateFiles` 静默返回空**：`[System.IO.Directory]::EnumerateFiles()` 在损坏 exFAT 上不抛异常、直接给空集，而同一路径 `Get-ChildItem`/`Test-Path` 正常——用它建索引会把真实存在的 20 个文件误报为"缺失"；③ **"不参与递归枚举"的目录**：` DOCUMENT873` 与 `ZUSER249` 能按名访问、文件完好，但递归枚举与资源管理器都看不见，据此对账会得出"丢 20 个文件"。**2026-10-13 更正：它们是火绒（Huorong）的反勒索诱饵目录，不是文件系统损伤** —— 每个卷根都有固定两个（`PACKAGE187`/`ZDOCUMENT778`），是指向 `<盘>:\ProgramData\Huorong\Sysdiag\BaitRoot` 的 reparse point，内含**合成的假文件**（合法文件头 + 大量重复填充字节；实测 4 KB 内仅 10–16 个不同字节值）。零真实内容，被加密也无所谓 —— 这就是诱饵的目的。三个陷阱共同点：**都朝"数据丢了"的方向误导**，而结论若被采信会导致错误决策

**确切命令序列**（复现/回归都靠它）
```bash
建索引一律走 `bash scripts/`（或 `node `、Python `os.walk`），**不用** `[IO.Directory]::EnumerateFiles`；对账先统一口径到字节；**把火绒诱饵目录（`PACKAGE187` / `ZDOCUMENT778`）显式排除在统计外** —— 它们是合成的假文件、不是数据（见 `docs/operations/VOLUME-REBUILD.md` §5.3）；**先建基线清单再拷贝**，用清单逐条对账而不是数总数——基线生成脚本见 `docs/operations/VOLUME-REBUILD.md` §3
```

**怎么发现它（指纹）**
①两份数值口径不同却"看起来差 2.5 GB"；②对账脚本报缺失、但 `Test-Path` 对同名路径回 True；③递归总数比清单推算少、差值恰好等于那两个目录的文件数（本盘为 20）；④`Get-ChildItem -LiteralPath "<带前导空格的目录>"` 可正常列出内容

**含确切语法的解法**
**已写进 `docs/operations/VOLUME-REBUILD.md` §3（基线清单生成）与 §5（三个陷阱各一节）**；无自动守门（属一次性迁移流程，靠"先建基线、逐条对账、保留备份"的纪律）
