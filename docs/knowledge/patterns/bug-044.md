# 失败模式：**把依赖 `this` 的方法「取下来」再调用 ⇒ 静默返回 undefined，打穿整条重启链**（本分支自己造成的真实回归）

**来源**：`docs/BUG-REPLAYS.md` 第 44 条（使用层面故障台账，代码检查全绿但用起来才炸）。

**是什么**
**把依赖 `this` 的方法「取下来」再调用 ⇒ 静默返回 undefined，打穿整条重启链**（本分支自己造成的真实回归）

**根因（WHY）**
DSH 换基座时新增了 `sessionKeyOf()` 统一"这是哪个会话"的键，内部写成了 `const f = ctx.sessionManager.getSessionFile; f()` —— 而 pi 的实现是 `getSessionFile() { return this.sessionFile; }`（`vendor/pi/packages/coding-agent/src/core/session-manager.ts:1156-1158`），**解绑后 `this` 是 undefined** ⇒ 抛 TypeError ⇒ **被同一函数里的 try/catch 吞掉** ⇒ 返回 `undefined`。后果不是小错：模式记录键成了 undefined（`modes-sessions.json` 恒为 `{}`）、重启请求的 `targetSession` 也变 undefined ⇒ `/mode roleplay` 不再真的换档重启。**单元测试全绿**（我的 fake 用的是箭头函数、不依赖 `this` ⇒ 测试把 bug 当成了契约）

**确切命令序列**（复现/回归都靠它）
```bash
`PI_GOLDEN_SCENARIO=1 bash scripts/golden-tasks.sh`（留出集必须显式开）；单测新增反向探针：用**依赖 `this` 的类**做 fake（`npx vitest run custom/features/mode/__tests__/session-key.test.ts`）
```

**怎么发现它（指纹）**
留出集（`PI_GOLDEN_SCENARIO=1`）从 **33/33 掉到 11/33（模式切换）与 8/33（两实例隔离）**，失败点集中在"没触发真重拉/`targetSession=undefined`/`modes-sessions.json` 为空"；历史对照：这两个场景 **2026-10-14 都是 33/33 通过**（`/tmp/golden-full2.log`）⇒ 明确是本分支引入的回归。机制复现：`node -e 'const sm={f:"x",getSessionFile(){return this.f}}; const g=sm.getSessionFile; try{console.log(g())}catch(e){console.log("throws:",e.message)}'`

**含确切语法的解法**
**已修**：改为闭包调用（`() => sm?.getSessionFile?.()`）保住接收者，并在注释里写明"必须方法形式调用"与事故出处；新增反向探针单测（用真实现那样依赖 `this` 的类）⇒ 该写法以后会被立刻抓住。★ 教训：**fake 用箭头函数会把"依赖 this 的方法"这类 bug 保护起来** —— fake 应尽量模仿真实实现的形状（结节见 `docs/design/CODING-TRAPS.md` #15）
