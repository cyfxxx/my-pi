# 失败模式：**[部分修复 · 平台] supervisor 的实例身份用 bash `$$`，而 pi 报的是 Windows PID ⇒ admin 重启链路在 MSYS/Windows 上静默失效**

**来源**：`docs/BUG-REPLAYS.md` 第 37 条（使用层面故障台账，代码检查全绿但用起来才炸）。

**是什么**
**[部分修复 · 平台] supervisor 的实例身份用 bash `$$`，而 pi 报的是 Windows PID ⇒ admin 重启链路在 MSYS/Windows 上静默失效**

**根因（WHY）**
supervisor 以 `SUPERVISOR_OWNER_PID="${SUPERVISOR_OWNER_PID:-$$}"` 取身份（bash 的 PID），而 pi 写进请求的 `ownerPid` 是 **node 的 `process.ppid`** —— 在 Windows/MSYS 下那是 **Windows PID**，与 MSYS 自己的 PID 命名空间**永不相等**（实测 `$$`=1720 而 node 报 ppid=42248）。于是 supervisor 把**自家 pi** 写下的重启请求判为"别人的请求"而拒绝，主循环只跑一轮就退出**且不报错**。Linux 上两者同源，故一直没暴露

**确切命令序列**（复现/回归都靠它）
```bash
`bash -c echo $$` 与 `node -e process.stdout.write(String(process.ppid))` 在同一 bash 里取值**不等**即复现；端到端见 `bash scripts/test-supervisor.sh` 的主循环段；三值对照：`$(node -e process.stdout.write(String(process.ppid)))` 给 37112、直接跑给 45016、stub 报的父 PID 给 18176 —— 三者互不相等，说明 MSYS 的 fork/PID 映射在此层面不可靠
```

**怎么发现它（指纹）**
supervisor 测试里 8 项：`主循环跑满两轮（期望 2，实际 1）`、`ownerPid = 本 supervisor（ppid 链路）→ 请求被认领并执行（期望 2，实际 1）`、`轮次记录：两轮 restart → exit（期望 restart,exit，实际 exit）` 等。现场取证：stub 已正确写 `action:restart` 且 `ownerPid=process.ppid`，但 `rounds.jsonl` 记 `adminAction:"" decision:"exit"`

**含确切语法的解法**
**部分修复（16 项失败 → 8 项；103 通过）**。已修三处：① `lib-mode.sh` 的 `mode_session_arg` 只认 `/*` 而**丢弃盘符路径**（`D:/…`）⇒ 模式解析回落 default；② 测试侧路径形式：`modes.json`/`modes-sessions.json` 由 `node -e` 读取，把 MSYS 形式（`/tmp/…`）拼进 `$ROOT/$AGENT_DIR` 得 `/m/my-pi//tmp/…` ⇒ node **ENOENT** ⇒ `mode_resolve` 的 catch **无条件回落 full**（6 项会话模式断言全红的真因）；③ 直调用例改用"子进程会看到的父 PID"而非 bash `$$`。**剩余 8 项（主循环端到端）受 MSYS PID 语义阻塞**：supervisor 无法在 MSYS 下得知自己的 Windows PID，"自愈成真实 PID"的写法实测**反而是错的**（无改善且更复杂，已回退）。正解方向：由启动器（`run-my-pi.ps1`）在拉起 supervisor 时把 bash 进程的 Windows PID 显式传入，二者共用该值，而不是让 supervisor 自己派生。影响面：**Windows 上 admin 重启/切会话不可用**；Linux/Termux 不受影响
