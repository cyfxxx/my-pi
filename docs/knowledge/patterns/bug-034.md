# 失败模式：**Node 版本守门只在构建期、运行期没有 ⇒ 启动成功却在使用中崩（zstd 解压）**

**来源**：`docs/BUG-REPLAYS.md` 第 34 条（使用层面故障台账，代码检查全绿但用起来才炸）。

**是什么**
**Node 版本守门只在构建期、运行期没有 ⇒ 启动成功却在使用中崩（zstd 解压）**

**根因（WHY）**
`build.sh` 第 1 步与 `doctor.sh` 都有 Node >= 22.19 的逐段版本守门，但**运行期**没有同口径守门——`pi-supervisor.sh` 各处直接写裸 `node`。于是机器 PATH 上存在一个过旧 node 时（实测 `D:\App_X\Node` = 22.14.0），`my-pi.sh` 能正常启动、进入 TUI，然后在遇到 `Content-Encoding: zstd` 的 HTTP 响应时崩：`TypeError: zlib.createZstdDecompress is not a function`（`vendor/pi/node_modules/undici` 8.10.2 的 `fetch/index.js` 解 zstd 时**无条件**调用它，而该 API 要 Node 22.15+）。**报错点离根因极远**：看起来像 pi 自身或网络层有 bug。属第 27 条的同源延伸——同一个"版本前提"在构建期挡住了，在运行期漏了

**确切命令序列**（复现/回归都靠它）
```bash
判据：`node -e "console.log(typeof require(\"zlib\").createZstdDecompress)"` 应回 `function`；便携布局下核对实际生效的 node：`bash -c "MY_PI_NODE=/g/runtime/node/node.exe ./my-pi.sh --version"`（应打印 `[supervisor] node: ... (v22.23.3)` 且退出码 0）；反证：`env MY_PI_NODE= PATH="/d/App_X/Node:/usr/bin:/mingw64/bin" bash -c "./my-pi.sh --version"` 应在启动前即拒绝并打印版本指引
```

**怎么发现它（指纹）**
崩溃记录 `portable/agent/crashes.json` 里 `kind=uncaught_exception`、`message=zlib.createZstdDecompress is not a function`、栈顶是 `undici/lib/web/fetch/index.js`；`node -v` 显示 22.14.x（主版本同为 22 却是旧的）；`node -e "console.log(typeof require(\"zlib\").createZstdDecompress)"` 该机回 `undefined`

**含确切语法的解法**
**已硬化**：`scripts/pi-supervisor.sh` 新增 `_pi_node_ok()` 与 `NODE_BIN` 解析器（优先级 `MY_PI_NODE` → 便携布局 `<ROOT>/../runtime/node/` → PATH），**放在任何 node 调用之前**（含 package 子命令直通，否则 `set -u` 下 `NODE_BIN: unbound variable`），校验通过后 `export NODE_BIN` 供子进程继承，不达标时用 `lib-vendor.sh` 的 `node_version_hint` 打印升级指引；`run-my-pi.ps1` 负责传入 `MY_PI_NODE`；详见 `docs/operations/BUILD-PORTABILITY.md` §4.4
